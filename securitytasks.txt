TASK 4 — ADD HTTP SECURITY HEADERS VIA next.config.mjs
--------------------------------------------------------------------------------
STATUS : NOT DONE  (next.config.mjs has no headers() configuration)
PRIORITY: HIGH

Steps:
  Add a headers() export to next.config.mjs:

    async headers() {
      const securityHeaders = [
        { key: 'X-DNS-Prefetch-Control',   value: 'on' },
        { key: 'X-Frame-Options',           value: 'SAMEORIGIN' },
        { key: 'X-Content-Type-Options',    value: 'nosniff' },
        { key: 'Referrer-Policy',           value: 'strict-origin-when-cross-origin' },
        { key: 'Permissions-Policy',        value: 'camera=(), microphone=(), geolocation=()' },
        { key: 'Strict-Transport-Security', value: 'max-age=63072000; includeSubDomains; preload' },
        {
          key: 'Content-Security-Policy',
          value: [
            "default-src 'self'",
            "script-src 'self' 'unsafe-inline'",
            "style-src 'self' 'unsafe-inline'",
            "img-src 'self' data: https://lh3.googleusercontent.com",
            "connect-src 'self'",
            "frame-ancestors 'none'",
          ].join('; '),
        },
      ];
      return [{ source: '/(.*)', headers: securityHeaders }];
    }

Why: Without these headers, the app is vulnerable to clickjacking (X-Frame),
MIME-sniffing attacks (X-Content-Type), and cross-site script injection (CSP).

TASK 5 — ENFORCE HTTPS-ONLY COOKIES FOR JWT STORAGE
--------------------------------------------------------------------------------
STATUS : NOT DONE  (JWT is stored in localStorage — visible to any XSS attack)
PRIORITY: HIGH

Steps:
  a) Stop storing the JWT in localStorage. localStorage is readable by any
     JavaScript on the page; one XSS bug = full token theft.
  b) Issue the JWT as an HttpOnly, Secure, SameSite=Strict cookie:
       const cookieOptions = {
         httpOnly: true,
         secure: process.env.NODE_ENV === 'production',
         sameSite: 'strict',
         maxAge: 60 * 60 * 24,  // 24 hours
         path: '/',
       };
       response.cookies.set('auth_token', token, cookieOptions);
  c) Update verifyToken() in auth.js to read from cookies instead of the
     Authorization header.
  d) SameSite=Strict also prevents CSRF from foreign origins.

Why: HttpOnly cookies cannot be read by JavaScript, making token theft via XSS
impossible. This is the industry-standard approach for session management.

TASK 6 — INPUT VALIDATION AND SANITIZATION ON ALL API ROUTES
--------------------------------------------------------------------------------
STATUS : NOT DONE  (API routes accept raw req.json() with no schema validation)
PRIORITY: HIGH

Steps:
  a) Install a schema validation library:
       npm install zod
  b) Define a Zod schema for every API request body. Example for login:
       const LoginSchema = z.object({
         email:    z.string().email().max(254),
         password: z.string().min(8).max(128),
       });
       const parsed = LoginSchema.safeParse(await req.json());
       if (!parsed.success)
         return NextResponse.json({ message: 'Invalid input' }, { status: 400 });
  c) Apply similar schemas to signup, forgot-password, and all case/revision
     mutation routes.
  d) Never pass raw user input directly to Prisma — always use the validated
     and typed version.

Why: Without validation, attackers can send malformed payloads, oversized
strings, or injection-attempt characters that crash or abuse your backend.

TASK 7 — ENABLE ACCOUNT LOCKOUT AFTER REPEATED FAILED LOGINS
--------------------------------------------------------------------------------
STATUS : NOT DONE  (login route has no failed-attempt tracking)
PRIORITY: HIGH

Steps:
  a) Add failedLoginAttempts (Int, default 0) and lockedUntil (DateTime?)
     columns to the User table in your Prisma schema.
  b) In the login route, after a failed password check:
     - Increment failedLoginAttempts.
     - If failedLoginAttempts >= 5, set lockedUntil = now + 15 minutes.
  c) At the top of every login attempt, check:
     - If lockedUntil is set and in the future → return 429 with minutes remaining.
  d) On a successful login, reset failedLoginAttempts = 0 and lockedUntil = null.
  e) Provide an admin UI action to manually unlock accounts.

Why: Prevents brute-force attacks that guess passwords by trying thousands of
combinations. Complements rate limiting (Task 3) with persistence across restarts.

PRIORITY: MEDIUM

Sensitive actions that need logging:
  - Admin login / logout
  - Doctor or designer account approved, suspended, or deleted
  - Password reset triggered
  - Case created, updated, or deleted

Steps:

         id        Int      @id @default(autoincrement())
         actorId   Int

         targetId  String?
         metadata  Json?
         ip        String?
         createdAt DateTime @default(now())

  b) Write a logAction(actorId, action, targetId, meta, req) helper and call
     it in every sensitive route.
  c) Store the requester's IP from req.headers.get('x-forwarded-for').
  d) Expose a read-only Audit Log page in the admin panel.

Why: HIPAA / GDPR and general security best practice require an immutable audit
trail. Without it, you cannot investigate breaches or prove compliance.

PRIORITY: MEDIUM

Why: If the web server is compromised, a least-privileged DB user limits the
